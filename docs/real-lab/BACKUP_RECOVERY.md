## Current preferred manual ISO recovery procedure (NOT AUTHORIZED)

Use after the new VM's installation/validation in VM_PROVISIONING_RUNBOOK.md; no export/import/checkpoint/restore has been run. Fast reset and independent recovery are distinct. lab1's nested AVHDX/Standard checkpoints are protected reference data only, never a baseline source. Sections below preserve earlier optional scripted planning.

1. **READ-ONLY preparation:** record new target name/immutable ID, config version, attached disk paths and complete parent chains, VM settings, baseline page/config hashes, OS/Nginx/OpenSSH versions, management mapping, SSH public fingerprint and host HTTP evidence. Confirm automatic checkpoints disabled on this new VM. No private keys in evidence.
2. **BLOCKED storage selection:** actual backup destination UNKNOWN. Obtain approved exact new directory, volume UniqueId, physical disk/device or external-medium identity, free bytes, filesystem with large-file support and failure-domain assessment. Minimum free30GiB for clean20GiB disk+10GiB reserve; add actual ISO staging bytes if there (~32GiB minimum), logs/metadata/other growth. C is insufficient; E hosts VM/drill and cannot be its own independent backup. More data/chains require a revised budget.
3. **B3 STATE CHANGE:** cleanly shut down only the recorded new target (separate shutdown approval), verify Off. Confirm checkpoint inventory empty before the planned clean export. If any checkpoint/parent exists, stop and budget the complete chain; do not delete/consolidate it to force the assumption. Capture timestamp/elapsed-time start and operator/request ID.
4. **B3 STATE CHANGE:** in Hyper-V Manager select the exact new target → Export, choose approved new independent destination. Export configuration and complete required disk set, not a manually copied active disk. Do not overwrite an existing artifact. Verify export completion/error logs, all required config/disks and identity references; hash each file (SHA256), record relative path/length and original VM ID/baseline fingerprint, retain manifest independently/read-only. Local file hashing is read-only; saving manifest changes only evidence files. See [Microsoft export/import](https://learn.microsoft.com/en-us/windows-server/virtualization/hyper-v/deploy/export-and-import-virtual-machines).
5. **Separate fast-reset approval:** only after clean export is verified, create one reviewed offline baseline checkpoint on the disposable target; record exact snapshot ID/type and associated paths/growth reserve. Reverting this checkpoint is fast reset, not disaster recovery proof. No further snapshots without a revised budget/approval. Record baseline fingerprint for reset verification.
6. **B4 STATE CHANGE:** review export hashes/identity again; original remains Off. Hyper-V Manager Import Virtual Machine → choose export → **Copy the virtual machine (create a new unique ID)**; use approved absent drill/config/disk paths. Never register in place or restore original ID; those could consume/alias the backup/original. Finish import without starting. Record actual new VM ID and distinct paths; verify no disk references point into the retained export. Do not claim success solely from wizard completion.
7. **B4 STATE CHANGE before first boot:** set restored copy automatic start Nothing; disconnect all its virtual adapters, confirm Off and disconnected, identify by generated ID and rename recovery copy. Never select source/lab1 by ambiguous name. No imported saved state may auto-resume; source cold-Off export is a prerequisite. Retain original backup unchanged.
8. **Separately approved isolated console boot/config:** keep NICs disconnected; assign new approved distinct MACs, use VMConnect to set recovery hostname, fresh machine/SSH identity and reserved distinct management IP in MAC-bound Netplan. A restored filesystem starts with the source guest identity—record and deliberately replace clone identities before network attachment. Never copy lab1 values. Page/package baseline stays the same; identity changes are expected and logged independently. If addressing/identity cannot be made safe, leave copy isolated/quarantined.
9. **Separately approved reconnect/validation:** confirm original stays Off, no IP/MAC conflict, attach copy to reviewed existing switches. Verify console/boot, pinned fresh SSH fingerprint then authentication, independent host HTTP200/exact baseline page and hash, package versions/config and management routing. A TCP22 probe alone cannot pass. Record actual times/duration and check outcomes, including failures.
10. **Independent recovery criterion:** export/import and cold recovery must be driven from host/VMConnect, not guest SSH. Demonstrate the recovery sequence without using guest SSH as its control path; SSH is a later verification signal. No need to break SSH or firewall as an artificial fault. Baseline and host recovery proof remain UNKNOWN until an actual approved drill passes.
11. **Failure quarantine:** retain logs, generated IDs, paths, partial export/import and error state; leave learner/run access blocked and avoid further boots/connects. No automatic retry, snapshot removal, backup deletion, lease release or cleanup. Propose exact new-target rollback/cleanup separately with immutable ID and checked workspace paths; never remove parent files by hand. Preserve independent backup and original data.
12. **Handoff:** archive dated approvals, journal/evidence, source/copy IDs, backup device/volume/path+hash manifest, baseline/reset ID, timings and all checks. Only verified clean recovery can support a later live-lab review. No approval for live Nginx faults/Start Real Lab is implied. Optional advanced operator scripts still require their original validated config/source preconditions; manual operations must keep equivalent human audit/quarantine evidence.

## Gate A prepared recovery tooling

Use the same reviewed operator entry point with `checkpoint`, `reset`, `backup` or `restore-copy`; default remains plan. Actual ID must match the one and only `ticketsim-lab`, which must be Off, with all attached disks under its dedicated VM root. Fixed baseline checkpoint is fast reset only; reset requires its exact checkpoint ID. Backup exports the powered-off VM to a new directory on a different volume, inventories SHA256 hashes, VM ID and recorded baseline fingerprint in integrity.json; restore validates every file. Store that manifest and backup offline/read-only after creation. Hashes detect corruption, not malicious rewriting by a privileged operator.

Drill sequence for later approval: validate Ubuntu/Nginx/SSH and host HTTP baseline; save fingerprint and versions; cold export independent backup; record hashes; review restore-copy plan; import using Copy/GenerateNewId to a new destination with all NICs disconnected before import; record new ID. Keep original off. Before boot/network reconnect, assign distinct MACs and a different reserved management address using console with NICs isolated; keep automatic start disabled and confirm no duplicate addressing. Boot and inspect console, pin host key, authenticate SSH, probe HTTP from host and compare exact expected content/hash/status and Nginx version. Demonstrate recovery without guest SSH (the import/export flow runs on host). Record timestamps/duration and outcome. Do not count import success alone as verified recovery.

`Assert-LabRecovery` checks the completed operator evidence record for distinct identity/MAC/IP, boot/console, SSH key/authentication, HTTP content/status, package/OS version, baseline fingerprint, duration and host recovery without SSH. It is an evidence validator, not a live probe. Failed/incomplete evidence and every unfinished action retain the persistent lease. A process restart cannot release it. Review current actual state and archive the lease only after independent verification and explicit operator reconciliation; preserve request logs, do not edit them into success. No recovery drill or checkpoint has run in Gate A.

**UNKNOWN:** no independent backup of a dedicated disposable target, tested restore, baseline fingerprint or host-side recovery proof has been supplied. A Hyper-V checkpoint alone is not an independent backup. The successful `lab1` SSH login and VMConnect access are useful network/console evidence, not a recovery drill. `lab1` remains reference-only and must not be used for a restore experiment.

For future `ticketsim-lab`, the operator must document the immutable VM ID, sole lifecycle controller, image and disk set, backup method/location and creation time, integrity evidence, baseline fingerprint, and dated restore drill on the disposable target. Verify the restored guest from the host and an independent client: VM identity/state, management path, SSH host key/authentication, expected Nginx page and HTTP status. The drill must demonstrate a host-owned recovery path when guest SSH is unavailable. Record resource headroom for backup plus VM and any retention/rollback limits.

The backend profile carries `baselineId` and `recoveryProofId` only when independently established. A run cannot use an unknown or failed recovery verdict; after process interruption the durable lease remains blocked as `recovery_required`. Phase 1B-0 has no real restore implementation or permission to alter a VM. See [SECURITY.md](SECURITY.md) and [VM_PROVISIONING_PLAN.md](VM_PROVISIONING_PLAN.md).
